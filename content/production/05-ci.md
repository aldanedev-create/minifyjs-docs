# Lesson 5: CI, size budgets, and release verification

Automate the build and reject releases that fail functional or size checks.

## Define a meaningful budget

Measure the current application, then choose a limit appropriate to your product. This example uses 50,000 raw bytes as an illustrative limit, not a recommended universal target.

```python
from pathlib import Path

asset = Path("dist/app.min.js")
size = asset.stat().st_size
limit = 50_000
if size > limit:
    raise SystemExit(f"Asset budget exceeded: {size} > {limit} bytes")
print(f"Asset budget passed: {size} bytes")
```

Save this as `check_assets.py`. For chunked bundles, check both the total output and the assets needed for the initial route. Consider compressed transfer size too.

## Add a GitHub Actions workflow

```yaml
name: Build production assets
on: [push, pull_request]
jobs:
  assets:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: python -m pip install -r requirements.lock.txt
      - run: python build_assets.py
      - run: python check_assets.py
      - uses: actions/upload-artifact@v4
        with:
          name: production-assets
          path: dist/
          if-no-files-found: error
```

Add your application's existing functional test command after the build. Tests should exercise the generated assets, including dynamic imports and user interactions. Promote the artifact that passed those checks to deployment rather than rebuilding it with different dependencies.

## Record release inputs

Retain the Git commit, Python and MinifyJS versions, target, configuration, and asset checksums alongside each release. Pin tested dependencies and upgrade them deliberately.

## Check performance separately

Run benchmarks on a stable runner, using identical fixtures and recorded tool versions. Shared CI machines introduce timing noise; investigate a regression over repeated runs before treating it as a release blocker. Read the [benchmark guide](#/benchmarks/overview).

## Final production checklist

- Invalid source fails the pipeline.
- The optimized application passes its functional tests.
- Assets remain within the chosen raw and compressed budgets.
- All bundle chunks are deployed together.
- Source map visibility and legal notices are intentional.
- A rollback can restore the previous manifest and assets.

You now have a repeatable path from source to a tested production release.
